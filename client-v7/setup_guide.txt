============================================================
MUSE RELAY v7 — SETUP GUIDE (for Muse)
End-to-end encrypted edition (libsodium crypto_box)
============================================================
You (Muse) receive a setup bundle with these files: muse_client.py,
poller.py, relay_auth.py, crypto.py, keys.py, safety.py, AGENTS.md,
setup_guide.txt (this file), requirements.txt, run.sh, run.bat,
config.example.json, start_daemon.sh, restart_poller.sh.

READ THIS FIRST — the 4 risks, in plain words
1. If someone gets your Relay Session or your private key, they can
   pretend to be the owner. Keep both out of chat and out of any file
   other than the two 600-permission files named below.
2. This code is not from Meta / Muse. It was checked, but no one can
   promise 100% that a program only does what it says — the owner
   decided to install it anyway.
3. The daemon runs in the background all the time, even when the owner
   is not in this chat, and wakes Muse up to answer. Not all of that is
   visible inside the chat.
4. If the Relay Session leaks, ask the owner for a fresh one-time password
   and repeat STEP 5. If the private
   key is lost, the old message history is unreadable — that was
   accepted; there is no recovery.
If the owner is not comfortable with these 4 points: STOP. Using the
normal Muse chat is enough and safer. Do NOT install.
If the owner says "vẫn cài" (still install), do the steps below IN
ORDER, one step at a time, and wait for "đồng ý, làm bước này" before
each step that has an effect. If you hit an error, re-read the current
step and tell the owner clearly before trying another way.

STEP 1 — UNZIP
- Unzip the bundle into a fixed folder, for example:
  ~/muse-relay (Linux/macOS) or D:\muse-relay (Windows).
- Do all later steps inside that folder.

STEP 2 — CREATE THE PYTHON ENVIRONMENT
Run inside the folder you just unzipped:

    python3 -m venv .venv
    source .venv/bin/activate        (Windows: .venv\Scripts\activate)
    pip install -r requirements.txt

requirements.txt pins exact versions (requests, pynacl, cffi).

STEP 3 — PREPARE THE SUPABASE SCHEMA (the owner runs this once)
In the Supabase SQL editor of the owner's project, run:

    alter table messages
      add column if not exists ciphertext text,
      add column if not exists nonce text,
      add column if not exists sender_key_id text,
      add column if not exists enc_version int,
      add column if not exists alg text;

    create table if not exists relay_keys (
      id bigint generated always as identity primary key,
      endpoint text not null,
      public_key text not null,
      key_id text not null,
      verified boolean not null default false,
      created_at timestamptz not null default now(),
      revoked_at timestamptz
    );

Do NOT touch the old flow yet. The old "text" column stays for now: it
carries only the two fixed protocol signals ('...' typing, 'pong' ready)
and, during the opt-in migration window, pre-E2E rows. It is deleted in
a later phase, once the signals move into the encrypted envelope.

STEP 4 — FILL IN THE CONFIG VALUES (config.json)
Copy config.example.json to config.json and put in these values (the
owner gives them in the instruction):

    SUPABASE_PROJECT_ID      e.g. jnmi… (20 letters)
    SUPABASE_PUBLISHABLE_KEY e.g. sb_publishable_…
    SUPABASE_URL             https://<project id>.supabase.co
    MUSE_EMAIL               e.g. muse_design@muserelay.local

There is NO Relay Session in config.json in v7 — never write one there.
There is NO password in config.json either — the one-time password exists
only in memory during STEP 5. Never write any password into any file.
ALLOW_LEGACY_PLAINTEXT stays false unless the owner explicitly enables
the migration window; ENC_VERSION stays 1.

STEP 5 — LOG IN ONCE WITH THE ONE-TIME PASSWORD, THEN ROTATE IT
The owner gives you a one-time (throwaway) password in the official Muse
chat. Use it exactly once, in memory only — never write it into any file,
never send it anywhere else.

1. Log in once (curl, or the same call from Python with requests):
    curl -s -X POST "https://<project id>.supabase.co/auth/v1/token?grant_type=password" \
      -H "apikey: <publishable key>" -H "Content-Type: application/json" \
      -d '{"email": "<MUSE_EMAIL>", "password": "<one-time password>"}'
   The response contains an access_token and a refresh_token.
2. Install the session — the refresh token only — into state/session.json
   (chmod 600) and nowhere else:
    printf '%s' '<refresh_token>' \
      | python3 relay_auth.py install-session --config config.json
3. Immediately change the password to a fresh random password you
   generate yourself:
    curl -s -X PUT "https://<project id>.supabase.co/auth/v1/user" \
      -H "Authorization: Bearer <access_token>" \
      -H "apikey: <publishable key>" -H "Content-Type: application/json" \
      -d '{"password": "<new random password>"}'
   Do not write the new password into any file. Do not send it anywhere.
   The one-time password is dead from this minute on and is never used again.
4. Prove the saved session still works:
    .venv/bin/python muse_client.py --once
   It logs in with the saved session, does one round, and exits. If it
   reports no usable session, stop and tell the owner.
If the session ever dies, ask the owner for a fresh one-time password and
repeat this step. Never use a secret key, PAT, or service_role key as a
substitute — this side of the relay has none of those.

Branch B (you built your own Supabase): there is no throwaway password.
The password you set when you created the auth user IS the owner's web UI
password. Give it to the owner in the official Muse chat, never write it
into any file, and use it once yourself to log in and install the session
exactly as above — then do NOT rotate it (the owner needs it to log into
the web UI).

STEP 6 — RUN THE DAEMON (exactly ONE puller per folder)
The daemon (poller.py) pulls new messages, verifies + decrypts them into
state/inbox.jsonl, and pushes encrypted replies from outbox/ up to
Supabase, ~3 seconds per round. On first run it also generates the Muse
key pair into state/keys.json (chmod 600) and publishes the public key.

Start it with your platform's scheduled task: the task runs
`bash start_daemon.sh`, which starts the daemon only if it is not already
running. Register the task so the daemon starts again after it dies or the
machine restarts. The scheduled task is the supervisor — do not use nohup,
cron, or systemd.

For a first smoke test you may run the daemon once in the foreground:

    .venv/bin/python poller.py

(press Ctrl+C to stop it; the scheduled task starts it again.)

Windows (optional, foreground): double-click run.bat — but note the daemon
is the preferred background runner; run.bat runs muse_client.py instead.

A lockfile (state/puller.lock) makes sure exactly ONE puller runs — if
muse_client.py is already running, poller.py exits by itself, and the
other way round. NEVER run both at the same time on purpose.

STEP 7 — VERIFY THE KEYS OUT OF BAND (nothing works until this is done)
The daemon does NOT process any message until both keys are verified.
1. Check the daemon published the Muse public key and wrote the safety
   number:  python3 keys.py status --state-dir state
   and:          cat state/safety_number.txt
2. Read the safety number to the owner IN THE OFFICIAL MUSE CHAT (never
   through a relay message). The owner compares it with the number shown
   in the web UI (Settings → Security). If the numbers match:
       python3 keys.py verify --config config.json
   If they do NOT match: STOP. Do not verify, do not process messages —
   a mismatched number means a key may have been substituted. Tell the
   owner and re-check the keys on both sides.
3. The daemon log should then stop saying "keys not verified yet".

STEP 8 — WAIT FOR A TEST MESSAGE AND REPLY TO IT
- The owner sends a test message from the web UI; the daemon verifies +
  decrypts it into state/inbox.jsonl (one JSON per line; only process
  lines with role="user"). A dropped forgery is logged, never delivered.
- Reply by writing the file outbox/<thread_id>.txt (UTF-8) — 1 file = 1
  message for that thread. The daemon encrypts it, pushes it and deletes
  the file.
- The owner confirms the reply arrived → setup is complete.
- Only report "done" after you have really checked: the daemon log shows
  the start line, the test message went through send → decrypt → reply →
  encrypt, and exactly one puller is running.

STEP 9 — READ AGENTS.md CAREFULLY
Read all of AGENTS.md in the same folder and follow it while operating
this relay: the Dropbox-only rule for assets, the inbox/outbox protocol,
the E2E rules, the prohibitions, and the capability limits from the
project's tags. Note: the automatic thread-title feature was REMOVED in
v7 — do not re-implement it.

ADDITIONAL NOTES

1) How often does the daemon poll?
- Every ~3 seconds. A hook wakes Muse within ~10 seconds when a new message
  arrives; Muse's schedule also starts the daemon every 3 minutes if it died.
  The daemon check, the new-message hook, and the background run are three
  SEPARATE opt-ins — ask the owner about each one on its own; do not turn
  the whole package on by default.

2) What if the daemon dies?
- Transient network error → the daemon backs off by itself (1, 2, 4 … 60s).
- Machine restart → the scheduled task runs start_daemon.sh; the saved
  session (state/session.json) reconnects by itself.
- The cursor in state/cursor.json is atomic and persistent: processed
  messages are never re-read, new messages are never missed. NEVER edit
  cursor.json by hand; if it is corrupt, ask the owner — do not delete it.

3) What if the keys are lost or the safety number changes?
- state/keys.json missing after keys existed → the daemon REFUSES to start
  and reports a lost key. Do not let it silently generate a replacement.
  The fix is an explicit re-key: python3 keys.py rekey --config config.json
  (old history becomes unreadable), then verify the new safety number
  out of band again (Step 7).
- Web public key changed without a announced re-key → the daemon stops
  processing, logs a warning, and waits for re-verification.
- Suspected private-key leak → re-key immediately AND ask the owner for a
  fresh one-time password and repeat STEP 5. Only the session leaked →
  repeating STEP 5 alone is enough.

4) What can this Muse see?
- Only its own project's data. Every request is RLS-scoped by its own
  login: messages for other Muses are INVISIBLE to this client. Even with
  E2E, the daemon still cannot read other Muses' rows — and now it cannot
  read its own rows either unless they decrypt with the verified key.

5) The /status command
- The owner can send "/status" in any thread. Muse must answer it in the
  EXACT wrapper format from AGENTS.md section 2 (<<<STATUS>>> …
  <<<END_STATUS>>>) with the raw output of its platform's /status — the
  web UI shows the result in the usage bar under the composer.

6) What E2E does NOT protect
- A compromised endpoint (this machine, or the owner's browser) still sees
  plaintext — an endpoint must decrypt to read and reply.
- Metadata stays visible: who messaged whom, in which thread, at what
  time, how many messages.
- E2E does not replace tightening write access (RLS) on Supabase. Both
  layers work together.
