============================================================
MUSE RELAY v6.2 — SETUP GUIDE (for Muse)
============================================================
You (Muse) are setting up this relay FOR YOUR OWN OWNER, in your own
VM. Each owner gets their OWN relay: their own Supabase project, their
own daemon in your VM, their own 4 values for the UI. Never reuse
another owner's project, keys, email or password.

Bundle contents: muse_client.py, poller.py, relay_auth.py, AGENTS.md,
setup_guide.txt (this file), config.example.json, README.md,
requirements.txt, run.sh, run.bat, start_daemon.sh, restart_poller.sh.
There is NO config.json with real values in the bundle — you create it
from config.example.json in Step 3. There is NO state/ or outbox/
folder in the bundle — they are created on first run.

Follow the steps below IN ORDER. If you hit an error, re-read the
current step and tell the owner clearly before trying another way.
Do NOT touch a live relay folder that is already running while you do
this — set up in a fresh folder.

STEP 0 — THE OWNER'S OWN SUPABASE PROJECT (you do this, not the owner)
Before the daemon can run, the owner's own Supabase project must exist:
  1. In your browser, create (or use) a Supabase project for THIS owner
     only. Note the Project URL and the publishable key (Settings -> API).
  2. Run supabase/setup.sql (from the UI repo) in that project's SQL
     Editor — it creates the tables and the RLS policies. Do NOT run it
     in anyone else's project.
  3. Create the auth user for this Muse: Dashboard -> Authentication ->
     Add user, email like muse_<name>@muserelay.local, a relay-only
     random password (never reused anywhere else), and tick
     "Auto Confirm User". This matters: @muserelay.local cannot receive
     email, so a normal sign-up that needs email confirmation will
     NEVER be able to log in. If "Auto Confirm" was missed, the daemon
     will fail with a password-login error about email confirmation —
     fix it in the Dashboard, do not guess a workaround.
  4. Create the project row for this Muse (the web UI / setup.sql flow
     for your install — it must carry user_id = this auth user's id,
     so RLS scopes every request to this project only).

STEP 1 — UNZIP
- Unzip the bundle into a fixed folder, for example:
  ~/muse-relay (Linux/macOS) or D:\muse-relay (Windows).
- Do all later steps inside that folder.

STEP 2 — CREATE THE PYTHON ENVIRONMENT
Run inside the folder you just unzipped:

    python3 -m venv .venv
    source .venv/bin/activate        (Windows: .venv\Scripts\activate)
    pip install -r requirements.txt

requirements.txt only contains the libraries that are needed (requests) — it installs quickly.

STEP 3 — CREATE config.json (from config.example.json)
Copy config.example.json to config.json and fill in THESE values for
THIS owner only:

    SUPABASE_URL             https://<project id>.supabase.co
    SUPABASE_PUBLISHABLE_KEY  e.g. sb_publishable_…
    MUSE_EMAIL               e.g. muse_<name>@muserelay.local
    MUSE_PASSWORD            the relay-only password from Step 0.3

    RELAY_SESSION            OPTIONAL, legacy v6 only. Leave it out on
                             a new install. Only use it if this folder is
                             an existing v6 install that already has one.
    SUPABASE_PROJECT_ID      OPTIONAL. Only needed if SUPABASE_URL is
                             missing — the URL is built from it.

Then lock the file down and check the login BEFORE starting the daemon:

    chmod 600 config.json
    python3 relay_auth.py test-login --config config.json

What happens on first login (v6.2): the daemon exchanges MUSE_EMAIL +
MUSE_PASSWORD for a session (grant_type=password), saves the refresh
token to state/session.json (chmod 600), and then REMOVES MUSE_PASSWORD
from config.json by itself. Restarts after that need no password and no
RELAY_SESSION — they use state/session.json. If test-login fails, read
its message: "wrong MUSE_EMAIL / MUSE_PASSWORD, or the auth user has
not confirmed its email yet" means Step 0.3 was missed; a dead
RELAY_SESSION means mint a fresh one or use MUSE_PASSWORD instead.

SECURITY — read this before you paste anything:
- MUSE_PASSWORD must be relay-only and random. Never reuse the owner's
  Supabase Dashboard password, email password, or any other password.
- Never send a password or a session value in chat, email, or a shared
  file. If the owner types it into your secure form, that form is for
  storage you cannot read back for a background daemon — for this
  client, the password has to reach config.json (you write it there
  from what the owner gave you through the approved channel for this
  install, or the owner pastes it into the file themselves). Never put
  a Supabase secret key (service_role), PAT, or dashboard password
  anywhere in this folder.
- After first login, verify with: grep MUSE_PASSWORD config.json
  — it must print nothing. If the password is still there, stop and
  tell the owner; do not start the daemon with a password left in the file.

STEP 4 — RUN THE DAEMON (exactly ONE puller per folder)
The daemon (poller.py) pulls new messages into state/inbox.jsonl and pushes
replies from outbox/ up to Supabase, ~3 seconds per round.

Start it (Linux/macOS):

    nohup python3 poller.py >> state/poller.log 2>&1 &

or use the helper:  bash start_daemon.sh   (starts only if not running)

Windows (optional, foreground): double-click run.bat — but note the daemon
is the preferred background runner; run.bat runs muse_client.py instead.

A lockfile (state/puller.lock) makes sure exactly ONE puller runs — if
muse_client.py is already running, poller.py exits by itself, and the
other way round. NEVER run both at the same time on purpose.

Optional — systemd auto-restart (Linux):
Create /etc/systemd/system/muse-relay-<muse_id>.service:

    [Unit]
    Description=Muse Relay daemon (<muse_id>)
    After=network-online.target

    [Service]
    Type=simple
    WorkingDirectory=/path/to/the/unzipped/folder
    ExecStart=/path/to/the/unzipped/folder/.venv/bin/python poller.py
    Restart=always
    RestartSec=5

    [Install]
    WantedBy=multi-user.target

Then: sudo systemctl daemon-reload && sudo systemctl enable --now muse-relay-<muse_id>
(view logs with: journalctl -u muse-relay-<muse_id> -f, or tail state/poller.log)

STEP 5 — CONFIRM THE DAEMON IS LISTENING
Read the log (tail -f state/poller.log). On success you see:

    daemon start v6.2 — session login, RLS-isolated, one puller, ~3s per round
    daemon login OK — auth=password email=muse_<name>@muserelay.local
    (then, on the first message: "inbox +N new messages, cursor=…")

A login failure prints "fatal: …" or "cannot start: …" — most often the
password is wrong, the auth user was not auto-confirmed (Step 0.3), or
the RELAY_SESSION is dead. Fix that one cause, do not try another
credential type as a workaround without telling the owner.

When the daemon starts it automatically sends a 'pong' ready-signal to the
relay — the owner's web UI then shows this Muse as ready/unlocked. When new
messages arrive, the daemon also automatically posts '...' typing signals.
Both are internal signals sent by the daemon itself; the Muse never writes
them itself (and must never write a reply that is exactly '...' or 'pong').

STEP 6 — GIVE THE OWNER THE 4 UI VALUES, THEN TEST
Give the owner ONLY these 4 values, so they can open the static UI
(Cloud mode) and sign in themselves:

    SUPABASE_URL, SUPABASE_PUBLISHABLE_KEY, MUSE_EMAIL, MUSE_PASSWORD

The UI signs in with the SAME email + password in the browser
(signInWithPassword). That creates a SEPARATE session for the UI — it
does not rotate or revoke the daemon's session. Tell the owner: open
the link in Safari/Chrome, not in the in-app browser of Zalo/Facebook/
Messenger. Then:
- The owner sends a test message from the web UI; the daemon moves it into
  state/inbox.jsonl (one JSON per line; only process lines with role="user").
- Reply by writing the file outbox/<thread_id>.txt (UTF-8) — 1 file = 1
  message for that thread. The daemon pushes it and deletes the file.
- The owner confirms the reply arrived → setup is complete.

STEP 7 — READ AGENTS.md CAREFULLY
Read all of AGENTS.md in the same folder and FOLLOW IT: the
Dropbox-only rule for assets, the inbox/outbox protocol, the prohibitions,
and the capability limits from the project's tags. The owner can stop the
relay at any time — when they say stop, stop the daemon and the schedule.

ADDITIONAL NOTES

1) How often does the daemon poll?
- Every ~3 seconds. A hook wakes Muse within ~10 seconds when a new message
  arrives; Muse's schedule also starts the daemon every 3 minutes if it died.

2) What if the daemon dies?
- Transient network error → the daemon backs off by itself (1, 2, 4 … 60s).
- Machine restart → start_daemon.sh (or systemd) brings it back; the saved
  session (state/session.json) reconnects by itself.
- The cursor in state/cursor.json is atomic and persistent: processed
  messages are never re-read, new messages are never missed. NEVER edit
  cursor.json by hand; if it is corrupt, ask the owner — do not delete it.

3) What can this Muse see?
- Only its own project's data. Every request is RLS-scoped by its own
  login: messages for other Muses are INVISIBLE to this client. If you
  ever see 0 or 2+ projects in the log, stop and tell the owner.

4) The /status command
- The owner can send "/status" in any thread. Muse must answer it in the
  EXACT wrapper format from AGENTS.md section 2 (<<<STATUS>>> …
  <<<END_STATUS>>>) with the raw output of its platform's /status — the
  web UI shows the result in the usage bar under the composer.

5) If the password or session leaks
- Create a NEW password for the auth user (Dashboard -> Authentication)
  or mint a fresh RELAY_SESSION, update config.json, delete
  state/session.json, and restart the daemon. The old session stops
  working once replaced. Tell the owner what leaked and what you replaced.
